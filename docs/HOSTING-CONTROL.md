# Развёртывание KARMA CONTROL

Для существующей семьи обновите тот же Node.js deployment, на котором работает KARMA SYSTEM. Один процесс поддерживает исходящее соединение с Discord Gateway, обслуживает сайт и API на одном HTTP-порту и работает с существующей SQLite. На публичном адресе браузер использует HTTPS. Для этого варианта достаточно одного deployment и одного входящего порта.

## Обновление существующего deployment

1. Создайте снимок текущей базы командой `npm run backup`. Скачайте полученный файл за пределы deployment. Отметьте текущий каталог данных и имя выбранного Discord-сервера.
2. Загрузите файлы релиза, включая веб-ассеты, миграции и `package-lock.json`, поверх исходников. Сохраните действующие переменные, каталог с БД и его содержимое. При загрузке ZIP файл `package.json` должен оказаться в корне deployment. [Загрузка и настройка Startup](https://bot-hosting.net/docs/guides/set-up-a-deployment)
3. В **Domains** активируйте HTTPS-поддомен или подключите собственный домен. Скопируйте окончательный origin, например `https://karma.example.org`. Примерные имена в этой инструкции заменяются вашим реальным адресом.
4. В том же приложении Discord, которому принадлежит бот, откройте **OAuth2 → Redirects → Add Redirect**. Для приведённого примера добавьте ровно `https://karma.example.org/auth/callback`. Схема, хост, порт при его наличии и путь должны совпадать с адресом приложения. Веб-вход использует Authorization Code Flow и scope `identify`. Роли участника проверяет сервер через существующего бота в выбранной гильдии. [OAuth2 Discord](https://docs.discord.com/developers/topics/oauth2)
5. Заполните переменные из таблицы ниже. Если бот уже настроен, оставьте его действующий токен и настройки intents. Включение веб-панели не требует сброса токена.
6. В Shell проверьте runtime командой `node -e "console.log(process.version, typeof require('node:sqlite').DatabaseSync)"`. Проекту нужен Node.js 22.16 или новее и результат `function`. В корне проекта выполните `npm ci --omit=dev`. На время применения миграций остановите рабочий процесс и запустите `npm run migrate` с прежним `DATA_DIR`. При запуске бота также применяется проверка миграций.
7. Выберите команду запуска `npm start`. Если панель принимает только **Entry File**, укажите `src/index.js` и выставьте `NODE_OPTIONS=--max-old-space-size=132` для воспроизведения ограничения из npm-скрипта. Запустите один экземпляр приложения. Его HTTP-обработчик отдаёт статические файлы, API и OAuth с одного origin. [Выбор entry file](https://bot-hosting.net/docs/guides/set-up-a-deployment)

### Окружение

| Имя | Значение в панели хостинга |
| --- | --- |
| `WEB_DASHBOARD_ENABLED` | `true` включает веб-панель. `false` оставляет бот в прежнем режиме |
| `CONTROL_ORIGIN` | Канонический публичный HTTPS-origin, например `https://karma.example.org`, без пути и завершающего слеша |
| `CONTROL_GUILD_ID` | Discord ID сервера семьи строкой. При использовании резервного `GUILD_ID` проверьте, что это именно нужный сервер. `GUILD_ID` также определяет область регистрации команд |
| `APPLICATION_ID` | Application ID приложения KARMA в Discord Developer Portal |
| `DISCORD_CLIENT_SECRET` | Секрет OAuth2 того же приложения. Отметьте эту переменную как секрет |
| `DISCORD_TOKEN` | Действующий токен bot user. Отметьте эту переменную как секрет |
| `SERVER_PORT` | Выделенный провайдером порт. На хостинге используйте значение deployment |
| `DATA_DIR` | Прежний каталог данных бота, например `/home/container/data` при стандартном размещении |

## Проверка после запуска

1. Откройте публичный адрес с устройства вне хостинга. Проверьте действительный HTTPS-сертификат, загрузку страницы и переход по кнопке на домен Discord. В адресе авторизации проверьте свой Application ID, scope `identify` и зарегистрированный callback.
2. Войдите владельцем тестового сервера. Повторите с обычным участником в отдельном профиле браузера. Для участника без разрешений ожидается экран ограниченного доступа, а защищённый API не должен возвращать записи. После выхода проверьте повторный запрос из той же вкладки.
3. Сохраните личный черновик. Проверьте его после обновления страницы, а также отсутствие нового сообщения в Discord. Для отдельной проверки публикации используйте согласованный тестовый канал и подтверждение в Publishing Center.
4. Перезапустите deployment. Проверьте сохранность черновика, прежней настройки тира, старой Discord-панели и работу действующего бота. Сверьте RAM, CPU и свободное место по панели во время входа, открытия списка и публикации. Эти результаты требуют доступа к вашему deployment и тестовой гильдии.

| Симптом | Проверка |
| --- | --- |
| Домен возвращает 502 | Состояние процесса, `WEB_DASHBOARD_ENABLED`, привязка к `0.0.0.0`, совпадение с назначенным `SERVER_PORT` |
| Discord сообщает об ошибке redirect URI | Канонический домен из `CONTROL_ORIGIN` и точный `/auth/callback` в Redirects **того же** Discord Application |
| После входа показывается ограниченный доступ | `CONTROL_GUILD_ID`, наличие бота и пользователя в этой гильдии, актуальные ID управляющих ролей и их разрешения |
| После перезапуска видна пустая конфигурация | Абсолютный путь `DATA_DIR`, рабочий каталог и использованный deployment. Проверьте выбранную базу до ввода новых данных |

## Альтернатива с внешним HTTPS-прокси

Если требуется своё публичное имя, сначала используйте подключение домена самого хостинга. При наличии отдельного управляемого веб-хоста можно перенести на него только HTTPS-вход. В таком варианте браузер обращается к одному публичному origin, например `https://control.example.org`. Обратный прокси передаёт страницы, `/auth/*` и `/api/*` в тот же запущенный backend KARMA. SQLite, Discord-токен, OAuth-секрет и проверка каждой операции остаются в процессе бота.

Для внешнего прокси нужен доступный ему HTTPS-upstream с проверяемым сертификатом либо заранее настроенный закрытый защищённый маршрут до процесса. Для публичного upstream используйте его настоящее имя в HTTP Host и TLS SNI, включите проверку сертификата по доверенному CA. Внешний адрес занесите в `CONTROL_ORIGIN` и Redirects. Прокси должен сохранять заголовки `Origin`, `Cookie`, `Set-Cookie` и CSRF приложения, отключать общий кэш для защищённых страниц и API, исключать параметры OAuth callback из access-логов. Зарегистрируйте один внешний callback и проверьте возврат в тот же браузерный origin. [Параметры HTTPS-upstream в NGINX](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

Если deployment вообще не предоставляет достижимого маршрута, одного DNS или статической копии сайта недостаточно для входа и управления Discord. До появления защищённого маршрута бот может работать на текущем хостинге с `WEB_DASHBOARD_ENABLED=false`. Другой вариант — перенос единственного работающего процесса и согласованного снимка БД на хост с постоянным диском и HTTPS. Независимое копирование файла SQLite между двумя одновременно работающими экземплярами приводит к расхождению записей.
